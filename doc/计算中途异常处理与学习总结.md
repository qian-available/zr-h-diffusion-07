# 计算中途发现异常怎么办

本文用于 VASP 作业已经提交、但速度或输出看起来不正常时的快速判断。基本原则是：**先做只读检查，确认异常后再停止；保留原目录，在新的 retry 目录中修改和重算。**

## 一、先判断是不是真的异常

发现计算很慢时，不要仅凭墙上时间或 VASP 的大框 `WARNING/ADVICE` 立即取消。先检查：

```bash
squeue -u liuzhixiao
tail -n 30 OSZICAR
grep -c "F=" OSZICAR
tail -n 30 vasp.stderr
date; stat -c '%y  %s bytes  %n' OUTCAR OSZICAR vasp.stdout vasp.stderr
```

这些信息分别回答：作业是否仍在运行、电子自洽是否推进、完成了多少离子步、是否有明确报错、输出文件是否继续更新。

通常可以继续运行的信号：

- 队列状态为 `R`；
- `DAV:` 迭代持续增加，电子步最终达到 `EDIFF`；
- `F=` 数量逐渐增加；
- `OUTCAR` 或 `OSZICAR` 的时间和大小仍在变化；
- `vasp.stderr` 为空，或只有不影响运行的性能建议。

需要认真处理的信号：

- `vasp.stderr` 出现 `segmentation fault`、`abort`、`NaN` 或缺少输入文件；
- 间隔一段时间检查两次，所有主要输出均完全不更新；
- 发现 POSCAR 原子数、元素顺序、POTCAR 顺序、INCAR 或 KPOINTS 用错；
- 计算虽然在运行，但单位电子步或离子步成本已经明显不适合任务目标；
- 结构出现异常短键、能量或力明显发散。

`F=` 在 OSZICAR 中表示完成一个离子步后的自由能汇总，不是原子力。弛豫是否真正完成，还要检查：

```bash
grep "reached required accuracy" OUTCAR
grep "General timing and accounting" OUTCAR
grep "FORCES: max atom" OUTCAR | tail -n 5
```

## 二、停止、恢复与本次经验

确认需要停止时，使用作业编号：

```bash
scancel JOBID
sacct -X -j JOBID --format=JobID,JobName,AllocCPUS,Elapsed,State,ExitCode
```

停止后不要删除 `OUTCAR`、`OSZICAR`、`vasp.stdout`、`vasp.stderr`、`CONTCAR` 或 Slurm 日志，也不要直接清空原目录重跑。原目录是失败原因、机时消耗和方法变化的证据。应记录：

- Job ID、开始和停止时间；
- 停止原因；
- 已完成的电子步或离子步；
- 原参数与准备修改的参数；
- 是否允许继承 CONTCAR、WAVECAR 或 CHGCAR。

修改后的任务放入新的目录，例如：

```text
retry_dcu_01/
retry_02/
```

运行中的目录不修改输入文件。只有结构和电子设置兼容时才考虑续算；如果更改了 k 点、赝势、元素顺序或计算后端，优先冷启动，避免旧 WAVECAR 带来兼容问题。

本次任务的主要经验是：旧 T/O CPU 作业运行约12小时仍未完成第一个离子步，说明计算没有崩溃，但配置与玩具任务的成本目标不匹配。保留旧现场后，新任务改用 `4x4x3 + EDIFF=1E-6 + LREAL=Auto + 4 DCU`，约2小时完成5个离子步，证明“慢”需要通过实际吞吐量判断，而不能只看警告或主观等待时间。

以后提交昂贵任务时，先提交一个代表性算例：启动后5–10分钟确认没有输入错误，30分钟确认输出推进，1–2小时估算每个离子步耗时；速度合理后再提交同批其他任务。批处理本来就允许无人值守，睡觉或关闭网页终端不会影响作业，真正重要的是事先设定检查节点、保留现场并让方法变化可追溯。

更完整的日常维护和恢复规则见 [SCNet_project_maintenance.md](SCNet_project_maintenance.md)，服务器环境见 [SCNet_server_configuration.md](SCNet_server_configuration.md)。
